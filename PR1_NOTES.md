# PR 1 — CMS publishing contract (content + templates + renderer + CI validation)

This PR converts the static site into a data-driven, template-rendered site
whose canonical source of truth is `content/*.json` + `templates/*.j2`. The
generated HTML (committed to the repo, served by GitHub Pages) is verified
against the renderer output in CI.

## What's in this PR

- `content/*.json` — every editable string, image reference, and list from the
  live site, extracted into stable-ID JSON schemas.
- `templates/**/*.j2` — Jinja2 templates that reproduce the current HTML output
  from that content.
- `manifests/renderer.json` + `manifests/last_publication.json` — versioning
  scaffolds for the future desktop CMS app.
- `scripts/render.py` — Python renderer (Jinja2). Reads content/, writes HTML +
  `sitemap.xml` + `assets/data/jobs.json`.
- `scripts/validate.py` — Runs the renderer to a scratch dir and DOM-diffs each
  output against the committed HTML. JSON-LD blocks are compared as parsed
  JSON, `<style>` and other `<script>` blocks as whitespace-normalized strings,
  attribute sets are compared order-insensitively.
- `.github/workflows/validate.yml` — runs `python scripts/validate.py` on every
  push and PR to main.  **Job name / required check: `content-render-validation`.**
- `.gitignore`, `.gitattributes` — ignore render cache; enforce LF line
  endings on text files.

## What is NOT in this PR

- **No site changes.** Same content, same DOM, same JSON-LD payloads, same asset
  paths and `?v=` cache-bust tokens as the current live site. This PR is
  parity-only. If you diff `pages/contact.html@main` against `pages/contact.html`
  after this branch merges, nothing should change semantically.
- **No CSS/JS refactor.** Per-page inline `<style>` blocks and per-page inline
  `<script>` blocks are embedded verbatim in the per-page templates (via
  `{% raw %}` fences). De-duplicating them is a later PR.
- **No `sitemap-images.xml` regeneration.** That file has 50 photos × 3 formats
  and it's derivable from `content/gallery.json`, but I kept it static in PR 1
  because the current file is stable and adding another moving piece to the
  renderer wasn't worth the churn.  Adding it is a natural PR 2 task.
- **No `robots.txt` regeneration.** 3 static lines; not worth the plumbing.
- **No fix for pre-existing bugs.** Noted below, unchanged.
- **No `.git`, `CNAME`, `README.md`, `assets/img/*`, `assets/video/*`,
  `assets/docs/*`, `assets/css/*`, `site.webmanifest`, `f83b1c7938d2915638cb8091832ee4be.txt`
  changes.** All untouched.

## How to run locally

```powershell
cd C:\src\echelon-website
python -m pip install jinja2 beautifulsoup4 lxml
python scripts\render.py          # writes HTML into the repo
python scripts\validate.py        # renders to .render-cache/build and diffs
```

Both scripts require Python 3.10+. Renderer is deterministic — same input,
same output.

## Schema decisions and trade-offs

### 1. Neighbourhoods paragraph — raw HTML with allowlist

`about.neighborhoods.paragraph_html` is stored as raw HTML in `content/about.json`
because the source markup interleaves 8 `<strong>` runs with plain text and one
`&ndash;`. Modelling this as typed inline runs would have been more editor-work
than it's worth in PR 1. The desktop app should sanitize this field with a
strict allowlist (`<strong>`, `<em>`, `<a>` — nothing else) before saving.

Rendered via `{{ ... | safe }}` in the template. Auto-escape is ON everywhere else.

### 2. About-page intro paragraph — same rationale

`about.intro_html` uses raw HTML for the single `<span class="highlight">`
inside the greeting. Same allowlist rules apply.

### 3. JSON-LD generation — always from data, never as raw JSON

Every JSON-LD block is generated by the renderer via `build_*_schema()` helpers
in `render.py` and emitted as `{{ schema | tojson(indent=2) }}` in the
templates. Content files store the *underlying* data (address, faq items, jobs,
breadcrumbs), never the JSON-LD payload itself.  The validator parses JSON-LD
as JSON and deep-compares, so serialisation ordering is not an issue.

### 4. Cache-bust `?v=202606010606` — kept exact

Stored as `site.cache_bust`. `404.html` intentionally does NOT use it (the
committed file doesn't); the 404 template uses a bare `href="/assets/css/site.min.css"`.

### 5. Nav hrefs — resolved per page in the renderer

Each page has a different relative depth (`index.html` at root vs `pages/*.html`
one level down). The renderer computes per-page nav hrefs via `os.path.relpath`
so the template just iterates `nav_items` with pre-resolved `href` + `active`
flags. Same for `careers_href` and `contact_href`.

### 6. Gallery caption pool — DUPLICATED

The captions list is stored in `content/gallery.json` as the canonical list AND
is hardcoded in the inline JS in `pages/gallery.html.j2`. Reason: matching the
existing JS array literal exactly (through the validator's whitespace
normalization) is fragile, and this inline JS is destined for a later PR that
factors gallery JS into `assets/js/`. When that happens, the JS reads
`gallery.json` directly.

For PR 1, if you edit `gallery.json → caption_pool` and don't also update the
JS array, `validate.py` won't catch it and users will see stale captions.
Future editors of `gallery.json → caption_pool` should re-run the render
script AFTER the JS is refactored (PR 2 or later); today the JS wins.

### 7. `assets/data/jobs.json` — regenerated from `content/careers.json`

The existing careers-page client-side loader fetches `../assets/data/jobs.json`
at runtime. Rather than swap that out (a JS change), the renderer regenerates
`jobs.json` from `content/careers.json → jobs` on every build, with the exact
same 8-field ordering (id, title, category, type, location, short, details,
datePosted) and 2-space indent as the current file. Editors update
`content/careers.json`; the artifact stays in sync.

### 8. Deterministic output

- LF line endings (`html.replace("\r\n", "\n")` before write; `.gitattributes` enforces).
- 2-space indent in JSON-LD and jobs.json (`json.dumps(..., indent=2)`).
- `ensure_ascii=False` (matches current jobs.json which stores `3–5` as a real en-dash).
- No dict ordering assumptions — schemas are constructed in a fixed key order
  in `render.py`. JSON-LD reference order matches the current HTML.

## Pre-existing bugs I noticed and DID NOT fix

Per the PR brief, no bug fixes in PR 1. Noting them here for a follow-up PR:

1. **`pages/services.html`, line 306:** `<section id="main-content" id="waiting-list">`
   has two `id` attributes on the same tag. HTML parsers (and both `bs4+lxml`
   and browsers) keep only the first (`id="main-content"`), so the CSS selector
   `#waiting-list` in the inline styles matches nothing. My template
   reproduces the bug verbatim so parity holds.

2. **`pages/gallery.html` line ~197:** `@media (max-width: 768px) { }` — an
   empty media query, presumably a leftover from a refactor. Harmless but
   noise.

3. **`pages/gallery.html`:** commented-out breadcrumb block (`<!-- <div class="breadcrumb">...`)
   between `</nav>` and `<main>`. My template reproduces the comment verbatim
   because the validator would flag its absence as a child-count mismatch.

4. **`pages/careers.html` CSS:** dangling selector fragments like `nav a:focus,`
   (followed by `.container { ... }`) and orphan `.footer-inner { ... }`
   outside of any media query — leftovers from CSS collapse. Rendered verbatim.

5. **`index.html`:** nested `@media (max-width: 420px) { }` empty block inside
   `@media (max-width: 768px)`. Same story — reproduce verbatim.

6. **`404.html`:** missing viewport meta compared with other pages. Whether this
   is intentional (404 is chrome-less) or a miss isn't for PR 1 to decide. My
   `templates/404.html.j2` matches the source.

7. **Nav `aria-current="page"`:** consistent across all pages EXCEPT that the
   nav toggle button is present on every standard page including small ones
   where the nav might not be present. Not a bug — just noting.

## Known deviations from byte-identical output — all safe

The validator uses semantic comparison (parse both with `bs4+lxml`; compare
tree structure, attributes, whitespace-normalized text). Byte-level output
differs but semantically nothing changes:

- **Whitespace inside tags:** Jinja2 output has different indent than
  hand-written HTML (my templates use 0-indent inside blocks; source varies).
  Whitespace-normalized text nodes are identical.
- **`<style>` block whitespace:** validator collapses whitespace runs to a
  single space before comparing.  Same CSS characters, same order.
- **`<script>` block whitespace:** same treatment.
- **JSON-LD serialisation:** JSON-LD is compared as parsed JSON. If Python's
  `json.dumps` and the human who hand-wrote the source picked different
  formatting or key orderings for a dict, that's invisible to the check.  Key
  order is preserved as-emitted (Python 3.7+ preserves insertion order and
  `render.py` emits in fixed order).

If a browser would render the two files differently, the validator will catch
it. Byte-diff on committed HTML vs render output is expected.

## How to add the "content-render-validation" check as required

In the GitHub repo settings for `feat/cms-publishing-contract` → main:

1. Settings → Branches → Branch protection rules → Add rule for `main`.
2. Require status checks to pass → search `content-render-validation` (the job
   name from `.github/workflows/validate.yml`).
3. Save.
